### 1-2. 흩어진 구조 요약

- 데이터 저장소가 **세 갈래**다. ① 강좌 · 교재 `S.pays`(운영자 문서 JSON + 학습자 이벤트), ② 학원 `S.bills`(운영자 문서 JSON, 학습자 `bill-pay` 이벤트), ③ 시설 `fac_*` 표(운영 서버 정규 표).
- 시연판은 모두 브라우저 문서(`S`)이고, 운영은 ①②가 `tenant_state` 문서 + `learner_events`, ③만 정규 표다. 즉 **합산 · 기간 · 수단별 집계를 SQL로 낼 수 있는 곳은 시설뿐**이다.
- 수납 수단 문자열이 제각각이다: `S.pays.method`(신용카드 · 계좌이체 · 간편결제 · 가상계좌, `lshop.js:158`), `S.bills.paid.method`(현금 · 카드 · 계좌이체 · 온라인 결제), `fac_payment.method`(toss · card_onsite · cash · bank · free).

### 1-3. 빠진 곳 · 중복 · 숫자가 안 맞을 수 있는 곳

1. **강좌 · 교재 현장 결제가 없다.** 데스크에서 성인 학원 수강료나 교재를 카드 · 현금으로 받아도 입력할 곳이 없다(대표님 지시의 핵심 공백).
2. **학원 청구서에 환불이 없다.** 퇴원 · 중도 환불은 수납 취소로 지우거나 별도 메모 처리 → 매출 보고에 환불이 안 잡힌다(`scn-k12.js:205`).
3. **매출 합산 기준이 화면마다 다르다.**
   - `sales2.js:213~214` 매출 = 결제 완료 · 부분 환불 · 환불 완료 · 환불 신청 + 청구서 `현장 납부`만.
   - `sales2.js:231~233` 통계 = 청구서 `status !== '미납'` 전부(**취소 · 부분 납부도 청구 전액**으로 합산될 수 있음).
   - `mods.js:42` 대시보드 매출 = 결제 완료 30일 + 청구서 `!== '미납'`(같은 문제).
   - `cls2.js:460` 월별 매출은 `환불 신청`을 매출에 포함, `부분 환불`은 차감 → 환불 신청 중 금액이 매출로 보임.
   - k12 `allPays`(`scn-k12.js:208`)는 `paid[]` 기준(부분 납부 정확). → **같은 달 매출이 화면에 따라 달라질 수 있다.**
4. **귀속월 기준이 없다.** `p.at`(결제 일시), `b.payAt || b.due`(납부일 또는 마감일), `b.month`(청구 월)을 화면마다 섞어 쓴다. 선납(`prepay`, `:284`)은 결제월 ≠ 귀속월이다.
5. **시설 매출이 어디에도 안 들어간다.** `S.pays`/`S.bills`를 합산하는 대시보드 · 보고서(`dash26.js:36`, `dashx.js:101`, `mods.js:402`)에 `fac_payment`가 없다 → 체육시설 이용권 매출은 대표 화면에서 누락.
6. **환불 규정이 3벌이다.** 시설(`fac/calc.js` 공식), 강좌(`ai.js:34` 문구 초안, 자동 계산 없음), 학원(없음). 학원법 · 평생교육법 환불 기준은 저장소 근거 문서가 없다(`docs/compliance/README.md:24`는 「학습비 반환 · 적용 규칙」 기능 언급만, 수치 없음) → **근거 확인 필요**.
7. **PG 승인 검증이 강좌 · 청구서에는 없다.** 시설만 서버가 토스 confirm으로 금액을 확인(`fac/pay.js`, `mod-pub.js:47`). 강좌 결제는 데모 결제창 결과를 이벤트로 받아 저장(`lshop.js:180~183`), 쿠폰 건만 서버가 금액 재계산(`app.js:234`). 청구서 `bill-pay`도 금액 서버 대조 없음.
8. **멱등 보장이 일부만 있다.** 시설은 `idem` · `fac_pay_order` 유일 색인, 강좌 pay 이벤트는 `xid`(`app.js:243`)가 있으나 유일 제약 확인 안 됨, 청구서 `bill-pay`는 `status==='미납'`일 때만 반영(`lshop.js:47`)하는 정도다.
9. **중복 가능 지점:** 시설 이용권 구매자가 강좌 수강생이기도 한 경우(`pass-course`), 같은 사람의 결제가 `S.pays`와 `fac_payment`에 각각 남는다(원장 도입 시 사람 단위 조회에서 합쳐 보여야 함).
10. **증빙은 표시만.** 현금영수증은 번호 표시만(`scn-k12.js:203` 안내 문구 「실제 발급은 연동 후」), 세금계산서 · 카드 영수증 서버 연동 없음. 영수증 화면(`crm-rcpt`)은 자체 양식.
11. 교재 **재고**, 보증금 **예수금**, 연체료 **별도 매출** 구분이 없다.
12. 개인정보: `S.pays`에 이름이 아닌 `who`(회원 id)만 저장되어 비교적 양호하나, `S.bills.paid.cr`(현금영수증 식별번호)은 학생 `crm.cr`에서 읽는다(`:260`) — 원장에는 번호를 복제하지 않는다.

## 2. 목표 모델 — 하나의 「수납 원장」

핵심 원칙: **원장은 돈의 사실(결제 · 환불 · 정산)만 기록하고, 무엇을 샀는지는 원천(강좌 · 청구서 · 예약 · 이용권 · 대여)이 설명한다.** 원천 화면은 그대로 두고, 금액이 움직일 때마다 원장에 한 줄이 쌓인다.

### 2-1. 흐름

```
주문(order)      무엇을 사려 하는가 (강좌 · 교재 · 청구서 · 예약 · 이용권 · 대여)
  └ 청구(charge)   받아야 할 돈 한 줄(품목 · 금액 · 귀속월 · 기한 · 쿠폰 할인 포함)
      └ 수납(receipt) 실제로 들어온 돈 한 줄(수단 · 일시 · 처리자 · 증빙)  ← 1 청구에 N 수납(분할 · 부분 납부)
          └ 환불(refund) 나간 돈 한 줄(원 수납 연결 · 규정 계산 · 확정 · 수단)  ← 부분 환불 가능
미수 = 청구 − 수납 + 환불확정(자동 계산, 저장하지 않음)
```

### 2-2. 용어 사전

| 구분 | 값 |
|---|---|
| 품목 유형 `item_type` | `tuition`(학원 월 수강료) · `course`(강좌 수강료) · `book`(교재) · `facility`(시설 예약) · `pass`(이용권) · `rental`(대여료) · `deposit`(보증금, **예수금 — 매출 아님**) · `late_fee`(연체료) · `fee_other`(차량비 등) · `discount`(할인, 음수 줄) |
| 결제 수단 `method` | `pg_card` · `pg_easy` · `pg_vbank`(가상계좌, 결정 필요) · `pg_overseas`(해외) · `term_card`(카드 단말) · `cash` · `bank` · `voucher`(바우처 · 이용권) · `offset` · `free` — 확장 열거와 승인번호 · 카드사 · 할부 · 단말 ID · 부분 취소 여부 · 해외 통화 · 환율 · 바우처 필드는 `02-voucher-coupon-refund.md` §1(기존 `toss`/`card_onsite`는 `pg_card`/`term_card`로 이관) |
| 청구 상태 | `open`(미수) · `partial`(일부 수납) · `paid` · `void`(취소, 수납 0일 때만) |
| 수납 상태 | `ready`(결제 대기) · `paid` · `failed` · `cancelled`(미확정 취소) |
| 환불 상태 | `pending` → `done` / `cancelled` (시설 `fac_refund`와 같은 3단계) |
| 증빙 | 카드 영수증(토스 `receipt.url` 저장, 온라인만 자동) · 현금영수증(**식별번호 서버 보관 안 함 · 발급 여부 표시와 안내만**) · 세금계산서(**안내만**: 사업자번호 · 발행 요청 메모 기록, 실발행은 세무사 · 홈택스) |
| 날짜 기준 | `paid_at`(결제일 · 현금주의, 마감 · 시재용) · `period_ym`(귀속월 · 발생주의, 월 매출 보고용). 선납 · 연장은 월별로 쪼개 귀속(§2-4) |
| 기관 분리 | 모든 표에 `tenant_id` + RLS(`tenant_iso`, `10_fac.sql:98~105`와 같은 정책) |

### 2-3. 개인정보 최소 원칙

- 원장에는 `sid`(학습자 계정 id)만 둔다. 이름 · 연락처 · 현금영수증 번호 · 카드번호는 원장에 저장하지 않는다(표시 때 회원 표에서 조인, 내보내기는 마스킹 옵션 기본값 「이름 첫 글자 + ○」).
- 보호자가 결제하면 `payer_sid`(보호자 계정) 별도, `sid`(원생)는 귀속 대상이다.
- 보관: 전자상거래법상 계약 · 대금결제 기록 5년을 근거 후보로 하되 **기관 확인 필요**로 표기(개인정보 보관 기간 설정값과 별도 취급).
- 학습자 응답은 본인 · 연결된 보호자 행만(`/api/pub/<tid>/me/...`), 직원은 역할별 범위(§4).

### 2-4. 귀속 · 분할 · 선납 규칙

- 월 수강료: `period_ym` = 청구 월. 선납 N개월은 청구 N줄(월별)로 만들고 수납 1건을 N줄에 배분(`alloc`).
- 이용권 연장: 기존 이용권 만료일 다음 날부터 새 기간. 청구 줄은 새 기간의 시작 월에 귀속(기간이 두 달에 걸치면 일수 비례는 2차, 1차는 시작 월 귀속).
- 쿠폰 · 할인: 청구 안의 음수 줄(`discount`)로 남겨 「정가 − 할인 = 청구액」을 항상 복원 가능하게 한다.
- 환불: 환불이 확정된 날 `paid_at`에 음수 줄로 반영, 귀속은 **원 청구의 월**과 **환불 확정 월** 중 선택(기본 = 확정 월, 세무 확인 필요).

## 3. 시나리오

화면 이름은 §4 제안 이름을 쓴다. 「직원」 = 데스크 직원(수납 권한), 「원장」 = 정운영자(owner).

### ① 학원 월 수강료 청구 → 보호자 온라인 결제 or 데스크 카드 → 미납 알림 → 부분 납부

| 단계 | 보이는 것 | 할 일 | 예외 |
|---|---|---|---|

### 4-2. 학습자 · 보호자 「결제 · 청구서」(학습자 앱 `lshop.js` 확장)

- 한 화면에 **청구서(미납) · 결제 내역 · 환불 · 이용권 · 영수증**을 모은다. 보호자 계정은 연결된 자녀별 탭.
- 지금의 「내 결제」(`mypay`), 「청구서」(`bill`), 시설의 「내 이용권 · 예약」(`lfac.js`)이 흩어진 진입점을 이 한 곳으로 모으고, 기존 라우트는 유지(링크 호환).
- 표시는 원장 조회(`GET me/ledger`) 기준. 데모는 기존 S 문서를 변환해 같은 모양으로 보여 준다.

### 4-3. 기존 화면과의 연결 방식(원천 = 원장)

| 기존 화면 | 연결 방식 |
|---|---|
| 시설 「현장 결제 · 정산」(`fac.js`) | 입력 · 환불 로직은 유지. 저장 시 원장에 같은 건을 쓰는 서버 함수 호출. 정산 탭은 「원장 보기」(시설 필터) 링크로 대체해 단계적 축소 |

### 5-3. 기존 데이터를 원장으로 모으는 방법 · 이중 기록 방지

1. **쓰기 경로를 한 곳으로 모은다(핵심).** 새 서버 함수 `ledger.record(c, tid, {...})` 하나만 원장에 쓴다. 시설(`fac_payment` 입력부 `mod-admin.js:123`, 토스 승인 `mod-pub.js:60`), 강좌 pay 이벤트(`app.js` eventsRoute), 청구서 수납(`bill-pay`, 운영자 수납)이 모두 이 함수를 호출한다.
2. **시설은 두 단계로 이관.** 1단계: `fac_payment`/`fac_refund`는 그대로 두고 원장이 **같은 트랜잭션에서 한 줄을 추가**(`led_receipt.legacy_ref='fac_payment:fp_...'`, 유일 색인으로 이중 기록 방지). 2단계: 정산 · 보고 화면이 원장만 읽는 것을 검증한 뒤 `fac_payment`를 원장 뷰로 대체 검토. (시설 규칙 · 테스트 벡터 `tests/fac-vectors.json`은 건드리지 않는다.)
3. **강좌 · 교재(`S.pays`)와 청구서(`S.bills`)는 문서 JSON이므로 일회성 이관 스크립트**를 둔다: 기관별로 `legacy_ref = 'pay:<id>' | 'bill:<id>:<paid.id>'`를 키로 `insert ... on conflict do nothing`. 재실행 안전. 이관 전후 합계 대조 보고서(금액 · 건수 · 환불)를 출력하고, 차이 0이 아니면 해당 기관은 전환하지 않는다.
4. **전환 방식은 기관 단위 플래그**(`ledger_on`). 켜기 전에는 기존 화면 그대로, 켠 뒤에는 운영자 화면이 원장에 쓰고 `S.pays`/`S.bills`는 **읽기 전용 호환 사본**으로 남긴다(옛 코드가 읽는 화면 보호). 켠 뒤에도 옛 경로에 입력하면 서버가 거절해 이중 기록을 막는다.
5. **시연판(브라우저 문서)**: 원장 모양의 `S.ledger[]`를 두고, 기존 입력 함수가 쓰기 어댑터를 거쳐 양쪽에 같은 `legacy_ref`로 기록(운영과 같은 규칙으로 중복 방지).
6. **금액 서버 재계산**: 클라이언트가 보낸 금액은 신뢰하지 않는다. 강좌는 게시본 가격 + 쿠폰(`server/coupon.js` `priceOf · calc` 재사용), 청구서는 `led_charge` 잔액, 시설은 기존 견적 함수. 불일치 시 400.
7. **멱등**: 모든 쓰기 요청에 `idem` 키 → `led_receipt.idem_key` 유일 색인. 토스 승인은 `toss_order_id` 유일 + 토스 `Idempotency-Key`(`fac/pay.js`의 `cf-<orderId>` 방식 재사용). 같은 `paymentKey` 재전송은 첫 결과를 그대로 돌려준다.
8. **토스 웹훅(2차)**: 결제창을 닫아 승인 호출이 누락된 건을 `ready` → `paid`로 보정(`fac/sweep.js`의 만료 청소와 같은 자리에서 점검).
