대표님 지시(2026-11-14): 「학원은 오프라인 pg 및 van 연동까지 해야돼. 복지관도 마찬가지야. 바우처 결제까지 있어. 토스 및 여러 페이먼트 · van사들의 결제 정책을 벤치마크하고 쉽게 연동할 수 있게 설계해줘.」
범위: 기획 문서만(코드 수정 없음). 선행 문서: `01-scenario.md`(수납 원장 모델 · `method` · 마감 시나리오 ⑤).
표기: **[확인]** = 아래 출처 URL에서 직접 확인, **[확인 필요]** = 출처에서 확인하지 못함(추측하지 않음, 계약 전 해당 사에 문의).

## 1. 결론 먼저

1. **웹 서비스가 카드 단말을 직접 제어하는 표준 방식은 없다.** 단말은 VAN사(또는 단말사) 전용 프로그램 · 라이브러리가 제어한다. 따라서 디디쌤은 단말 제조사를 하나씩 붙이지 않고, **「결제 어댑터」 계층**(원장은 하나, 어댑터는 방식별 교체)으로 설계한다.
2. 방식은 세 가지로 나뉜다. ① **데스크 PC 로컬 에이전트**(KSNET KSCAT 등 VAN 프로그램 연동) ② **클라우드/스마트 단말 SDK**(토스 프론트 플러그인 등, 앱이 단말 안에서 실행) ③ **수기 기록**(단말은 따로 쓰고 결과만 입력).
3. **바우처는 시스템 직접 연동이 아니라 「전용 카드/단말로 결제 + 원장에 기록」이 1차 현실이다.** 바우처 승인 · 정산은 각 제도 운영기관이 맡고, 제공기관 연동 API 공개 근거를 확인하지 못했다([확인 필요]).
4. **1차 추천: 수기 기록 모드(전 업종) + 학원 데스크 로컬 에이전트 1종(KSNET KSCAT 기준 또는 선택 VAN) + 토스 프론트 플러그인은 2차 파일럿.**

## 4. 설계

### 4-1. 결제 어댑터 계층(핵심)

```
스튜디오(수납 화면)
   └ pay-adapter 인터페이스: request(금액, 청구 id, 수단) → 결과 이벤트 / cancel(승인 ref, 금액)
        ├ ManualAdapter      (수기 기록, 1차 필수)
        ├ LocalAgentAdapter  (데스크 PC 데몬 ↔ VAN 프로그램, 1차 학원)
        ├ CloudTerminalAdapter (토스 프론트 플러그인 등, 2차 파일럿)
        └ VoucherAdapter     (수기 기록 + 바우처 필드, 1차)
결과는 어느 어댑터든 동일한 「단말 결제 결과」 형식으로 원장(수납 receipt)에 기록
```

### 4-2. 데스크 결제 흐름(LocalAgent / CloudTerminal 공통)

1. 직원이 청구서의 「수납」 → 수단 「카드(단말)」 선택, 금액(기본 잔액) 확인.
2. 스튜디오가 **수납 요청**(`pay_req_id` 멱등키, 금액, 청구 id)을 서버에 `pending`으로 먼저 기록 후 에이전트/단말에 전달.
3. 단말에서 고객이 카드 삽입 · 서명(KSCAT 사례: 5만원 이상 서명패드 [확인]).
4. 결과(승인번호 · 카드사 · 매입사 · 할부 · 일시 · 마스킹 카드번호 · VAN 거래키)가 스튜디오로 돌아오면 서버가 `paid`로 확정, 원장 수납 1줄 생성.
5. 영수증: 단말 인쇄 또는 문자 전송(토스 패키지 A는 문자만 [확인]), 우리 화면에서는 「수납 내역」 링크.
6. **결과가 안 오는 경우**(네트워크 끊김 · PC 재시작): `pending` 요청이 30분 이상이면 「확인 필요」 목록에 올려 직원이 단말 영수증을 보고 「승인됨(수기 확정)」 또는 「실패」 처리. 토스 플러그인은 단말 캐시로 재조회 가능(14일 [확인])하나 KSNET은 [확인 필요].
7. 취소: 원 승인 ref로 취소 요청. KSNET 사례처럼 **원 카드 재삽입이 필요할 수 있어** 「카드 없이 취소」는 사에 따라 다름(토스 플러그인은 NICE VAN만 [확인]).

### 4-3. 수기 기록 모드(단말 미연동 기관용, 전 업종 기본)

- 입력 필드: 수단(카드/현금/이체/바우처), 금액, 승인번호(카드일 때 필수 권장), 카드사 · 할부 개월(선택), 영수증 종류, 메모, 첨부(전표 사진 선택).
- 원칙: 수기 기록은 **「단말 확인 전」 상태 배지**를 붙이고, 일 마감 대사에서 단말 일계와 맞추면 「대사 완료」로 바뀐다.
- 중복 방지: 같은 승인번호 + 금액 + 일자는 경고(클래스업 2분 30초 중복 규칙 [확인]은 VAN 측 정산 규칙이므로 우리 쪽은 경고 수준).

### 4-4. 장애 시 수기 처리

단말 연동 실패 시 같은 화면에서 「수기 기록으로 전환」 한 번. 원장 줄에 `source='manual_fallback'`과 사유를 남긴다. 단말 자체 장애(결제 오류)는 재부팅 · 네트워크 전환 순으로 안내 [확인](토스 단말 가이드).

### 4-5. 일 마감 대사 화면(시나리오 ⑤ 연장)

| 구역 | 내용 |
|---|---|
| 시스템 합계 | 오늘 수납 · 환불을 수단별(카드 단말 / 수기 카드 / 현금 / 이체 / 바우처 / 온라인) 합계 |
| 단말 일계 입력 | 단말/VAN 일계 금액 입력(1차는 직원 수기 입력). 2차: VAN 매출 조회 연동으로 자동 채움(오늘얼마 사례처럼 NICE · KIS · NICE페이먼츠 VAN 매출 조회 연동 [확인]) |
| 차이 표시 | 시스템 − 단말 = 차이, 건별 매칭 목록(승인번호 기준), 미매칭 건 강조 |
| 대사 파일 | 정산 파일(일 대사)의 제공 형식 · 채널은 VAN별 [확인 필요]. 업로드(CSV 등) 형식을 어댑터가 흡수하도록 열어 둠 |
| 확정 | 차이 사유 입력 → 마감 확정(원장에는 정정 기록만 허용, 01 문서 ⑤와 동일) |

### 4-6. 원장 필드 요구(`01-scenario.md` §5 수납 표에 추가)

| 필드 | 설명 |
|---|---|
| `channel` | `online_pg` · `terminal` · `manual` · `voucher` |
| `terminal_id` · `merchant_no` | 단말 · 가맹점 번호(기관 설정에서 관리) |
| `approval_no` · `approved_at` | 승인번호 · 승인 일시 |
| `card_issuer` · `card_acquirer` | 발급사 · 매입사(응답에 있을 때만) |
| `installment` | 할부 개월 |
| `masked_card` | 마스킹 번호만(원번호 저장 금지, 01 문서 개인정보 원칙 유지) |
| `van_tx_key` | VAN 거래 일련번호(취소에 필요) |
| `pay_req_id` | 멱등키 · 단말 요청 상태(`pending`/`paid`/`failed`/`needs_check`) |
| `cancel_of` · `cancel_amount` | 원 승인 연결, 부분 취소 금액 |
| `cash_receipt_state` | 발행 여부 표시만(번호 미보관 원칙 유지) |
| `voucher_type` · `voucher_amount` · `copay_amount` | 바우처 종류 · 바우처 금액 · 본인부담금 |
| `recon_status` | `unmatched` · `matched` · `adjusted`(일 대사 결과) |
| `source` | `adapter` · `manual` · `manual_fallback` |

원장의 방향성은 `method`에 `card_terminal` · `voucher`를 추가하는 것이며 기존 `card_onsite`는 `channel=terminal` 또는 `manual`로 분리하는 안을 제안한다(결정 필요 아님, 구현 시 마이그레이션).

## 5. 1차 추천안(업종별 현실 기준)

| 업종 | 1차 | 2차 |
|---|---|---|
| **학원** | 수기 기록 모드 + 데스크 PC 로컬 에이전트 1종(이미 쓰는 단말의 VAN에 맞춰 선택. KSNET KSCAT 선례 [확인]) + 일 마감 대사(수기 입력) | 토스 프론트 플러그인 파일럿, VAN 매출 조회 자동 대사 |
| **복지관** | 수기 기록 모드 + **바우처 필드**(종류 · 바우처/본인부담 분리). 바우처 승인은 기존 전용 단말/절차 그대로 | 제도별 정산 파일 업로드 대사 |
| **체육시설** | 수기 기록 모드 + 현장 카드는 기존 시설 `card_onsite` 흐름 유지, 스포츠강좌이용권 · 문화누리카드는 `voucher` 수납으로 기록 | 클라우드 단말 연동 |

**필요한 제휴(추정이 아니라 확인해야 할 것)**
1. VAN 1곳과 개발 규격 공유 협약: KSNET(KSCAT 선례), NICE정보통신(토스 플러그인이 NICE VAN 사용). 후보 중 개발 규격을 실제로 제공하는 곳으로 선택 [확인 필요].
2. 단말 모델 1종 지정(탁상형 리더기 + 서명패드, 또는 토스 프론트 패키지 C 유선) — 모델은 VAN 호환 목록 확인 후 확정 [확인 필요].
3. 토스플레이스 파트너 개발자 접근 권한(플러그인 SDK 문서 외 외부 서버 호출 방식 확인) [확인 필요].
4. 바우처 제도 운영기관(사회보장정보원 · 평생교육진흥원 · 체육진흥공단 · 문화누리) 문의: 제공기관용 연동 가능 여부 [확인 필요].
