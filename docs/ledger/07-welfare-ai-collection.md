## 1. 결론 먼저

1. **복지관 수납은 「접수 → 감면 확인 → 결제 → 영수증」을 한 흐름(화면 3개 이내)으로 묶는다.** 접수에서 감면 · 바우처가 자동 계산되어 결제 화면에는 「받을 금액」 한 줄만 크게 보인다(§3).
2. **감면 자격은 증빙 사본을 저장하지 않고 「확인함」 이력(확인자 · 일시 · 자격 종류 코드 · 유효기간)만 남긴다.** 복지관마다 감면 대상 · 비율 · 대리 접수 가능 여부가 달라(§0 S1~S3) 표준값을 박지 않고 **기관 설정표**로 둔다.
3. **AI는 「제안 → 사람이 확인 버튼 → 실행 → 되돌리기」** 한 가지 모양만 쓴다. 이미 있는 AI SAM 확인 카드(`scxPlan`, `didisam/samctx.js:27`)와 되돌리기(`undoBtn`, `didisam/slim-ai.js:201`), 학원 자동 운영(`scn-k12.js:303~311` AUTO 목록)을 그대로 재사용한다(§4). **돈이 움직이거나 감면 · 자격이 바뀌는 일은 자동 확정하지 않는다.**
4. **대시보드의 모든 숫자는 원장 요약 함수 하나가 만든다.** 대시보드 · 보고서 · AI SAM 답변 · 내보내기가 같은 함수를 부르고, 화면 푸터에 기준(귀속월 / 결제일)을 항상 표시한다(§5).
5. **데스크 결제 연동 1차 안**: 04 · 06 문서 결론을 복지관에 그대로 적용한다. 결제 어댑터 인터페이스(수기 / 로컬 에이전트)를 복지관 수납 화면에 처음부터 넣고, 단말 규격 확보 전에는 수기 어댑터가 같은 흐름으로 동작한다. 연동 수준 Lv0 · Lv1 · Lv2를 정의해 「연동됨」의 기준을 못 박는다(§6).
6. 후원금은 **수강료 원장과 섞지 않는다.** 후원금은 영수증 발급 · 전용계좌 · 지정 용도 관리 의무가 따로 있어 수입 유형을 분리해 기록한다(§3 W6).

## 3. 복지관 수납 시나리오 (화면 단위)

화면 이름은 `01-scenario.md` §4의 스튜디오 「매출 · 수납」을 따른다. 복지관 전용 진입점은 「접수 · 수납」 한 곳(접수와 현장 수납 통합)이며 탭 안에서 W1~W5가 이어진다. 「직원」 = 수납 권한 직원, 「관장」 = 기관 정운영자.

**심플 원칙(설계 기준)**
- 접수에서 결제 완료까지 **버튼 누름 최대 6회**(이용자 검색 → 프로그램 선택 → 감면 확인 → 금액 확인 → 수단 선택 → 결제 완료).
- 화면에는 **받을 금액 한 줄**(정가 − 감면 − 바우처 지원금 = 본인부담)만 크게 보이고 계산 근거는 「자세히」로 접는다.
- 어르신 · 장애인 이용자 대면이 많아 **큰 글씨 · 큰 버튼** 모드(기관 설정 기본 켬, `sitepro.js`의 시니어형 구성 참고).

| 2 | 프로그램 목록(정원 · 잔여 · 요일 · 수강료 · 재료비). 이용자 구분에 맞는 프로그램을 위로 | 프로그램 선택(복수 가능) | 정원 확인, 중복 접수 경고(같은 과목 중복 — S1은 동일 과목 1과목 제한, **기관 설정** `dup_rule`), 청구 초안 생성(정가 + 재료비) | 정원 초과: 대기 접수 또는 추첨 대상으로 등록(S1 추첨 사례, 기관 설정). 대기 접수는 **청구를 만들지 않음** |
| 3 | 「누가 접수하나요」 선택: **본인 / 대리인(가족 · 보호자) / 직원 대행** | 대리인이면 관계(자녀 · 배우자 · 보호자 · 기타)와 「이용자 의사 확인함」 체크 | `agent_sid`, `agent_rel`, `consent_checked`(예/아니오 · 확인자 · 일시)를 접수에 기록. **대리인의 이름 · 연락처는 수신 알림용으로만 사용**(원장에는 `payer_sid` 계정 id) | **기관 설정 `allow_proxy`가 꺼져 있으면 대리 접수 선택 비활성**(S1처럼 방문 본인 접수만 허용하는 기관 대응). 아동은 보호자 `payer_sid`가 기본 |
| 4 | 접수 요약: 프로그램 · 시작일 · 금액(감면 전). 「다음: 감면 확인」 | 확인 | 접수 상태 `pending_pay`(결제 전). 결제 안 하고 닫으면 「오늘 할 수납 일」 카드에 올라감(§4 A7) | 이용자가 이미 같은 기간 수강 중이면 중복 접수 차단 |

화면 수: 이용자 선택 · 프로그램 선택 · 접수자 선택은 **한 화면 3구역(세로 스크롤 없이)**.

### W2. 감면 자격 확인 (증빙 「확인함」만 기록, 사본 저장 안 함)

원칙: **증빙 사본(촬영 · 스캔 · 업로드)을 시스템에 저장하지 않는다.** 직원이 눈으로 확인하고 「확인함」을 누른 사실만 남긴다. 근거: S2는 증빙을 「개강 시 확인」하는 방식이고, 감면 정책은 기관마다 다르다(S1~S3). 자격 정보는 민감 가능성이 있어 최소 처리한다(§0 읽지 못한 것 7).

| 단계 | 화면 · 보이는 것 | 직원이 하는 일 | 시스템 처리 | 예외 |
|---|---|---|---|---|
| 1 | 접수 요약 아래 **감면 확인 카드**: 이용자에게 이미 유효한 확인 이력이 있으면 「감면 확인 이력 있음 · 유효기간 ○월 ○일」 한 줄. 없으면 자격 목록(기관 설정표: 예시 수급자 · 차상위 · 장애 · 경로 · 국가유공자 · 한부모 · 다자녀) | 이력이 유효하면 **확인 불필요**(그대로 적용). 없으면 이용자가 내민 증빙을 보고 해당 자격을 선택 | `led_elig_check`(§3-A) 한 줄 생성: 자격 종류 **코드**(`basic`·`near_poor`·`disabled_severe`·`disabled_mild`·`senior`·`merit`·`single_parent`·`multi_child`·`other`), 증빙 종류 **코드**(`id_card`·`certificate`·`app_screen`…), 확인자, 확인 일시, 유효기간 | 증빙이 없으면 「일반 요금」으로 진행 + 「나중에 확인」 표시(유예, 기관 설정 `grace_days`)해 유예 만료일에 카드 알림 |
| 2 | 감면 적용 결과: 「정가 3만원 − 감면 1.5만원(경로 50%) = 1.5만원」. **정책은 기관 설정표**에서 가져오며 값은 하드코딩하지 않음 | 확인 | 서버가 정책 · 중복 규칙 재계산(02 §2-5, 클라이언트 값 불신). **여러 자격에 해당하면 가장 유리한 하나만 적용**(S2 방식)이 기본값, 기관이 「중복 허용」을 선택 가능 | 기관 정책에 「수급자 3과목 무료」(S1) 같은 **과목 수 한도형 면제**는 `scope.max_items`로 표현. 한도 초과분은 정가 적용 |
| 3 | 직원 화면 표시는 「감면 대상」 여부와 감면액까지. **자격 종류는 관장 · 지정 담당만 조회**(02 §2-4 주의 유지) | — | 감사 로그에 확인 · 변경 이력(누가 언제), 조회 이력 | 자격 종류가 영수증 · 알림 문구 · 내보내기 기본 열에 **나오지 않음** |
| 4 | 유효기간 만료 전 알림: 「감면 확인이 ○일 뒤 만료되는 이용자 N명」 | 다음 접수 때 다시 확인 | 만료 후 접수 시 카드가 다시 뜸. 자동 연장 금지(연장은 직원이 다시 확인) | — |

## 4. AI 수납 · 미납 자동화 설계

### 4-1. 원칙 — 「사람은 확인 버튼만」

| 단계(자동화 수준) | 의미 | 대상 | 되돌리기 |
|---|---|---|---|
| **L0 보기** | AI가 숫자 · 목록을 보여 줌 | 우선순위, 요약, 이상 감지 목록 | 해당 없음 |
| **L1 확인 카드** | AI가 초안을 만들고 직원이 **확인 버튼 1번**(AI SAM `scxPlan`과 같은 모양) | 청구 생성 · 미납 안내 대량 발송 · 분할 제안 · 환불 처리 · 대사 후보 | 확정 전 취소 · 확정 후는 항목별 규칙 |
| **L2 자동 실행 + 알림** | 기관이 처음 한 번 규칙을 켜면 이후 자동. 실행 결과를 「오늘 한 일」에 기록 | D-3 납부 안내처럼 **돈이 안 움직이는 안내**, 정확히 일치한 입금 대사 | **예약 발송 취소**(발송 전), 대사 취소 · 정정 기록 |
| **L3 관장 승인** | 금액 기준 초과 · 감면/자격 변경 · 바우처 환수 | 환불 승인, 감면 이력 수정, 마감 후 정정 | 02 §3-6 승인 단계 |

공통 규칙
1. **돈 · 자격이 확정되는 일은 L2로 올리지 않는다**(환불 확정 · 감면 적용 · 수납 확정 · 마감).
2. **AI는 숫자를 만들지 않는다.** 숫자 · 날짜 · 대상 목록은 원장 함수와 규칙이 계산하고 AI는 문장 · 후보 순위 · 설명만 만든다.
3. **감면 · 고령 · 장애 · 수급 여부를 미납 예측 점수의 입력으로 쓰지 않는다**(취약 이용자에 대한 불공정 대우 방지 **[설계]**).
4. **감면 · 바우처 대상 이용자에게 가는 독촉은 기관 설정으로 제한**: 기본은 문자 · 알림 독촉에서 제외하고 담당자 전화 제안만 한다(결정 D2).
5. 실제 문자 · 알림톡 전달은 업체 연동 후 시작(현재 학원은 「알림 등록」까지, `scn-k12.js:238` 문구와 동일). 연동 전에도 규칙 · 카드 · 기록은 동작한다.
6. 학원 자동 운영 설정 구조(`CFG().auto`, `scn-k12.js:303~311`, 켜고 끄기 `:317`)를 복지관도 같은 방식으로 쓴다(키 예: `wbill` · `wpre` · `wlate` · `wmatch` · `wanom` · `wbrief`).

### 4-3. AI SAM 대화 명령 예시 15개

기존 AI SAM의 규칙 엔진에 복지관 명령을 추가한다(학원의 수납 명령 `scn-k12.js:236~240`과 같은 확인 카드 방식). 「수준」은 §4-1 기준, 모든 L1 이상은 `scxPlan` 확인 카드로 응답한다.

### 4-4. 매일 아침 「오늘 할 수납 일」 카드

**발송 규칙 [설계]**: 평일에만 만든다. **주말 · 공휴일에는 자동 브리핑 · 알림을 보내지 않는다.** 휴관일 기관 설정을 따른다.

```
오늘 할 수납 일 · 11월 17일(월)                             [모두 확인]
─────────────────────────────────────────────────────────
 1  청구 초안 확인        128건 (감면 9 · 바우처 12 · 경고 3)      [확인]
 2  오늘 연락할 분        5명 (D+7 경과 2 · 약정일 도래 1)        [전화 목록]
 3  입금 대사 확인        후보 4건 (자동 처리 11건 완료)           [확인]
 4  이상 감지             3건 (중복 의심 1 · 청구 누락 2)         [확인]
 5  환불 승인 대기        2건                                    [관장 확인]
 6  바우처 정산 청구      이번 달 청구 가능 18건, 마감 3일 전       [확인]
 7  어제 마감 · 현금 예입  마감 미확정 0 · 예입 확인 1건           [확인]
 8  감면 확인 만료 예정   4명 (이번 주)                           [확인]
─────────────────────────────────────────────────────────
 AI 요약: 이번 달 순매출 4% 증가, 미납 3건 7일 경과
```

- **항목은 건수가 0이면 숨긴다**(빈 카드는 만들지 않음). 항목마다 「확인」 한 번에 해당 확인 카드로 이동하며, **「모두 확인」은 L1 위험이 낮은 항목(청구 초안 중 경고 없는 건 · 후보가 아닌 안내)에만** 적용한다.
- 홈 배치는 학원 홈 「자동 운영」 섹션(`scn-k12.js:347~354`)과 같은 위치 · 같은 컴포넌트를 재사용한다.
- 직원과 관장은 같은 카드를 보되 L3 항목(환불 승인 · 마감 후 정정)은 관장에게만 활성.

### 4-5. 장애 · 오작동 대응

| 상황 | 처리 |
|---|---|
| AI가 만든 청구 초안이 틀렸다 | 확정 전이면 폐기 · 수정, 확정 후는 `void`/정정. 수정 이유는 학습 데이터가 아니라 규칙 설정(`지침`)으로 반영 |
| 잘못된 안내가 나갔다 | 발송 후 회수 불가. 「정정 안내」 템플릿 제안(L1). A3 문구는 템플릿이라 오류 범위가 작음 |
| 대사가 틀린 청구에 붙었다 | 대사 취소 → 수납 `ready` 복귀 → 정정 기록 |
| 자동화가 의심스럽다 | 「설정」 한 곳에서 항목별 끄기. 끄면 즉시 중지(`k12-auto` 동작과 동일, `scn-k12.js:317`) |
| 알림 연동 장애 | 「알림 등록」까지만 기록(현재 학원과 동일). 전달 실패 목록은 A7 카드에 표시 |

## 5. 매출 대시보드

### 5-1. 모든 화면이 같은 원장 숫자를 쓰는 기준 **[핵심]**

현재는 같은 달 매출이 화면마다 달라질 수 있다(`01-scenario.md` §1-3 3 · 4번: `sales2.js:213~214` · `sales2.js:231~233` · `mods.js:42` · `cls2.js:460` · `scn-k12.js:208`이 각자 다른 합산 · 귀속 기준). 복지관 대시보드는 이를 되풀이하지 않기 위해 다음 규칙을 **정의로** 못 박는다.

| # | 규칙 |
|---|---|
| R1 | **숫자의 원천은 원장 요약 함수 하나**(`ledger.summary(from, to, basis, filters)`, 01 §5-2 `GET /api/ledger/summary`). 대시보드 위젯 · 보고서 · 기관 보고 · AI SAM 답변 · 내보내기 · 홈 카드가 모두 이 함수를 부른다. 화면 코드에서 `S.pays` · `S.bills`를 직접 합산하지 않는다. |
| R2 | **기준은 두 가지뿐**: 귀속월(`period_ym`, 기본) · 결제일(`paid_at`, 현금주의). 화면 푸터에 항상 「기준: 귀속월 · 서버 집계 시각 · 원장 N행」을 표시하고, 기준을 바꾸면 달라지는 이유 한 줄(선납 · 환불)을 보인다(01 ⑥ 유지). |
| R3 | 같은 필터(기간 · 기준 · 프로그램 · 수단)를 주면 **어느 화면에서도 같은 숫자**가 나와야 한다. `tests/ledger-vectors.json`(01 §5 계획)에 「같은 필터로 대시보드 · 보고서 · AI SAM 응답 · 내보내기 합계가 일치」 케이스를 둔다. |
| R4 | 모든 카드 숫자는 클릭하면 **원장 행 목록**으로 이동(근거 추적). 마감된 월의 숫자는 정정 기록으로만 변한다. |
| R5 | **후원금 · 보조금은 이용 매출에 포함하지 않는다.** 「수입 총계」 보조 줄에 별도 표시한다(`income_kind` 분리, §2). 보증금 · 예수금도 매출 아님(01 §2-2). |
| R6 | 환불은 **환불 확정 월**에 음수로 반영(01 §2-4 기본, 세무 · 회계 확인 후 확정 — 01 결정 5 연동). |
| R7 | AI 요약 · 카드의 증감률은 같은 함수로 전월 · 전년 값을 같은 기준으로 계산한다(§5-4). |

### 5-4. AI 요약 문장

**방식**: 문장은 템플릿 + 조건으로 만들고, **수치 토큰은 원장 함수 결과를 치환**한다(AI가 숫자를 쓰지 않음, §4-1 공통 규칙 2). LLM을 쓰더라도 입력은 「지표 값 객체」뿐이며 객체에 없는 숫자는 출력하지 못하게 검증한다. 문장 속 숫자는 클릭하면 해당 원장 행으로 이동(R4).

| 조건(임계값은 기관 설정) | 문장 템플릿 | 예시 |
|---|---|---|
| 순매출 전월 대비 변화 ≥ ±2% | 「이번 달(N일 기준) 순매출이 전월보다 {x}% {증가·감소}했습니다.」 | 이번 달 순매출 4% 증가 |
| 기한 경과 미납 건 존재 | 「미납 {n}건 중 {k}건이 {d}일 이상 경과했습니다.」 | 미납 3건 7일 경과 |
| 미납률 전월 대비 상승 | 「미납률이 {a}%로 전월({b}%)보다 {p}%p 올랐습니다.」 | — |
| 바우처 정산 대기 > 0 | 「바우처 정산 대기 {won}(청구 가능 {n}건), 청구 마감 {d}일 전입니다.」 | — |

## 6. 데스크 결제 연동 필수 반영 — 1차 확정 제안

04 · 06 문서가 정한 사실: 웹 서비스가 카드 단말을 직접 제어하는 표준은 없고, 단말은 VAN사 · 단말사 전용 프로그램이 제어한다. 결제선생에는 단말 연동이 없다. 1차 추천은 **수기 기록 모드(전 업종) + 데스크 PC 로컬 에이전트 1종 + 일 마감 대사**이다(04 §5, 06 §4). 복지관에는 다음으로 확정하자고 제안한다.

### 6-2. 복지관만의 추가 고려

- **창구 속도**: 어르신 · 장애인 이용자는 단말 조작이 느릴 수 있다. 결제 대기 화면에 **「단말에서 결제해 주세요」 큰 글씨 · 취소 버튼 · 재시도 버튼**을 두고, 대기 시간 제한은 두지 않는다(단 `pending`은 30분 후 확인 목록).
- **한 이용자 복수 프로그램**: 접수 시 여러 프로그램을 한 번에 결제할 때 단말 결제는 **합산 금액 1회**, 원장에는 청구별 배분(`led_alloc`, 01 §5-1)한다. 부분 환불은 단말 부분 취소 가능 여부(`partial_cancel_ok`)에 따라 안내(02 ⑧-4).
- **현금 중심 현장**: 복지관은 현금 · 이체 비중이 높을 수 있다 **[확인 필요: 기관별 수납 현황 수치 없음]**. 현금 흐름(권종 계산 · 시재 · 예입)을 카드 단말 연동과 같은 우선순위로 만든다.
