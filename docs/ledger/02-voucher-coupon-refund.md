## 1. 원장 필드 요구

원칙은 `01-scenario.md` §2(원장은 돈의 사실만, 개인정보 최소)를 따른다. 아래는 `led_receipt`(수납) · `led_refund`(환불)에 추가하는 컬럼과 열거값이다. PG · VAN 담당 문서가 정한 실제 응답 필드명에 맞춰 이름은 조정한다(여기서는 **무엇을 받아야 하는가**만 확정).

### 1-1. 결제 수단 `method` 확장(01 §2-2 대체)

| 값 | 설명 | 채널 | 부분 취소 |
|---|---|---|---|
| `pg_card` | 온라인 PG 카드(국내) | 온라인 | 가능(S4) |
| `pg_easy` | 간편결제(카카오 · 네이버 · 토스 등) | 온라인 | PG별 확인 필요 |
| `pg_vbank` | 가상계좌(결정 필요) | 온라인 | 환불 계좌 입력 필요(타 은행 이체) |
| `pg_overseas` | 해외 카드 · 해외 간편결제(PayPal 등) | 온라인 | PayPal 가능(S5), 해외 카드 PG별 확인 필요 |
| `term_card` | 오프라인 카드 단말(VAN) | 현장 | 단말 · VAN 정책별(04 문서) |
| `cash` | 현금 | 현장 | 해당 없음(현금 지급) |
| `bank` | 계좌이체(직접 입금) | 현장 · 온라인 | 해당 없음(계좌 환불) |
| `voucher` | 바우처 · 이용권(§2) | 현장 · 온라인 | 바우처 종류별 |
| `offset` | 쿠폰 · 이월 상계(원 단위 0원 수납 대체) | 내부 | 해당 없음 |
| `free` | 0원 | 내부 | 해당 없음 |

**한 건의 결제가 복수 수단일 수 있다**(바우처 + 본인부담 카드). 수납 1건 = 1수단, 한 청구에 N수납(01 §2-1의 `1 청구 N 수납`)으로 표현하고, 묶음은 `pay_group_id`로 연결한다.

| `settle_state` | PG · 단말 · 바우처 | `none`(해당 없음) · `pending`(정산 전) · `settled`(정산 후) — 취소 즉시 처리 vs 영업일 소요 안내(S4) |

| `recorded_by`, `idem_key`, `legacy_ref` | 공통 | 01 §5와 동일 |

### 1-3. 해외 결제 컬럼

해외 결제의 **정산 통화 · 환율 적용 방식은 PG 계약에 따르며 S5에 없으므로 「확인 필요」**. 원장은 어느 방식이든 담을 수 있게 아래를 받는다.

| 컬럼 | 의미 |
|---|---|
| `pay_currency` | 결제 통화(KRW · USD · JPY 등, ISO 4217) |
| `pay_amount_fx` | 결제 통화 금액(소수점 있는 통화 대응 위해 최소단위 정수 + `fx_minor_unit`) |
| `fx_rate` | 적용 환율(1 외화 = N원), `fx_rate_at`(기준 시각), `fx_rate_src`(PG 응답 · 은행 고시 · 수동) |
| `amount_krw` | **원화 환산 금액(원장 합계의 기준, 매출 집계는 항상 이 값)** |
| `fx_fee` | 해외 수수료(PG 해외 결제 수수료 · 카드 해외 이용 수수료 중 가맹점 부담분) |
| `fx_bear` | 환차 부담 주체(`merchant` · `payer` · `pg`) — PG 계약 확인 후 열거 |
| `settle_currency`, `settle_krw` | 정산 통화와 실제 정산 원화 → `환차손익 = settle_krw − amount_krw`(정산 완료 시 확정) |
| `payer_country`, `three_ds` bool | 국가 · 3DS 통과 여부(해외카드는 3DS 필요, S4) |

원칙: 원화로 결제창을 열어 외화 카드로 결제되는 경우(해외 발급 카드 + 원화 청구)와 외화로 청구하는 경우를 `pay_currency`로 구분한다. **원장 금액 합계 · 매출 · 환불 한도는 `amount_krw` 기준**이고, 환불 시 외화 금액 · 환율은 §3-5 규칙에 따른다.

### 1-4. 바우처 컬럼(`led_voucher`, 수납과 1:N)

| 컬럼 | 의미 |
|---|---|
| `voucher_kind` | `social_service`(사회서비스 전자바우처) · `lifelong_ticket`(평생교육이용권) · `sports_ticket`(스포츠강좌이용권) · `culture_card`(문화누리카드) · `local`(지자체 · 기관 자체 바우처) · `other` |
| `voucher_program` | 사업명(자유 문자열 + 코드표, 사업은 해마다 바뀜) |
| `gross_amount` | 서비스 이용 총액(= 지원금 + 본인부담) |
| `subsidy_amount` | **지원금**(바우처에서 차감되는 금액, 정산 청구 대상) |
| `copay_amount` | **본인부담금**(이용자가 직접 낸 금액 — 별도 `led_receipt`(카드 · 현금)와 `pay_group_id`로 연결) |
| `copay_receipt_id` | 본인부담 수납 연결 |
| `subsidy_claim_state` | `none` · `claimable`(청구 가능) · `claimed`(청구함) · `paid`(입금) · `rejected`(반려) · `clawback`(환수) |
| `claim_batch_id`, `claim_at`, `paid_at` | 정산 청구 묶음 · 청구일 · 입금일 |
| `voucher_ref` | 승인 · 사용 번호(카드 · 단말 · 시스템에서 받은 값. 수급자 번호 · 카드번호 전체는 **저장하지 않음**, 끝 4자리만) |
| `eligibility_kind` | 자격 구분(수급자 · 차상위 등) — 감면 쿠폰 자동 적용 근거(§2-7)로만 쓰며 **민감정보라 접근 권한을 별도 분리** |
| `period_ym`, `valid_to` | 이용 월 · 이용권 유효기간(월말 소멸 등 소멸 규칙은 사업별, S7·S8) |

**지원금 매출 처리**: 매출(수익)은 총액(`gross_amount`)이다. 지원금 부분은 입금 전까지 「미수금(기관 대상)」으로 따로 보이게 한다(미수 화면에서 이용자 미수와 분리). 정산 입금 시 `paid`로 바뀌고 매출 변동은 없다. 반려 · 환수가 나면 `clawback` 줄로 음수 반영한다.

## 2. 쿠폰 · 할인 정책(강좌 전용 → 전 품목)

### 2-1. 현재 코드의 한계(`파일:줄`은 v40.0 기준)

| 항목 | 현재 | 한계 |
|---|---|---|
| 대상 | `c.cls`(강좌 id 배열, `didisam/coupon.js:23` · `service/server/coupon.js:19`) | 교재 · 시설 · 이용권 · 청구서에 쓸 수 없음 |
| 형태 | `type`: `rate`/`amount`, `v`, `from`/`until`, `max`, `on`(`coupon.js` calc) | **상한(최대 할인액) 없음**, 최소 결제액 없음, 1인당 횟수 없음 |

| 발행 | 운영자가 1건씩 만들기, 코드 무작위 8자(`gen`) | 대량 발행 · 대상자 지정 · 자동 발행 없음 |
| 보고 | 쿠폰 카드에 코드별 사용 횟수만 | 할인액 · 정책별 매출 영향 보고서 없음 |
| 위치 | 매출 화면 아래 카드 | 청구서(`S.bills`) · 시설(`fac_*`)과 무관 |

### 2-2. 확장 모델 — 「할인 정책」(discount policy) 하나로 통일

쿠폰(코드를 입력해 쓰는 것)과 자동 할인(조건이 맞으면 붙는 것)을 **같은 정책 모양**으로 둔다. 차이는 `trigger`뿐이다.

| 필드 | 값 · 설명 |
|---|---|
| `id`, `name`, `on` | 정책 이름(보고서 표시명) · 사용 여부 |
| `trigger` | `code`(코드 입력) · `auto`(조건 충족 시 자동) · `staff`(직원 수동 적용, 사유 필수) |
| `scope.item_types` | `tuition` · `course` · `book` · `facility` · `pass` · `rental` · `fee_other` 중 복수(**보증금 `deposit` · 연체료 `late_fee`는 항상 제외**) |
| `scope.targets` | 특정 강좌 · 반 · 교재 · 시설 · 이용권 id 배열(비우면 해당 유형 전체) |
| `kind` | `rate`(정률) · `amount`(정액) · `fixed_price`(고정 가격으로 대체, 선택) |
| `v`, `cap`, `min_pay` | 값 · **상한**(정률일 때 최대 할인액) · 최소 결제액(미만이면 미적용) |
| `period` | `from` ~ `until` |
| `limit_total`, `limit_per_person` | 전체 횟수(기존 `max`) · 1인당 횟수 |
| `eligible` | 대상 지정: `sids[]` 또는 구성원 구분(`member_group`)  — 자동 · 지정 발행에서 사용 |
| `stack` | 중복 규칙(§2-5) `exclusive` · `stack_with_groups[]` · `priority` |
| `round` | 끝전 처리(기본 10원 미만 내림 — 기존 규칙과 동일, 정책별 변경 불가) |
| `funded_by` | 비용 부담: `org`(기관 자체) · `external`(지자체 · 후원, 정산 청구 대상 — 바우처와 구분 시 사용) |
| `report_tag` | 보고서 묶음 이름 |

계산 순서(청구 줄 하나 기준): ① 정가(게시 가격 · 얼리버드 등 기존 `priceOf` 결과) → ② 자동 정책 적용(우선순위 순) → ③ 쿠폰 코드 적용 → ④ 바우처 지원금 차감(§1-4). **원장에는 정가 줄 + 정책별 음수 `discount` 줄로 남겨** 어느 정책이 얼마를 깎았는지 복원 가능하게 한다(01 §2-4).

### 2-3. 발행 방식 4가지

| 방식 | 사용처 | 동작 | 비고 |
|---|---|---|---|
| 단건 | 운영자가 이벤트용 코드 생성 | 현재 「+ 쿠폰 만들기」 확장(품목 유형 · 상한 · 1인당 횟수 입력 추가) | 기존 쿠폰 모두 호환(없는 필드는 기본값) |
| 대상 지정 | 특정 학생 · 보호자 · 구성원 | 정책에 `eligible` 지정 → 지정자 계정에 「내 쿠폰함」 노출, 코드 노출 없이 선택 적용 | 타인이 코드를 알아도 못 쓰도록 `sid` 일치 검사 |
| 대량 | 행사 · 제휴 · 졸업생 | CSV 업로드 또는 N개 일괄 생성: 고유 코드 N개(코드별 1회용), 배포용 CSV 내려받기 | 코드 알파벳 혼동 문자 제외(기존 `gen`과 동일) |
| 자동 | §2-4 | 조건 충족 시 청구 생성 단계에서 자동 부여 | 부여 근거(조건 · 값)를 줄에 기록 |

### 2-4. 자동 할인 유형(학원 · 복지관 · 대학 공통 틀)

| 유형 | 조건 판정 | 데이터 근거 | 주의 |
|---|---|---|---|
| 형제 할인 | 같은 청구 월에 같은 보호자 연락처로 연결된 원생 2명 이상 수강 | k12 형제 연결(`scn-k12.js:81` 「같은 보호자 연락처면 형제로 연결」) | 몇째부터 · 정률 · 정액은 학원이 설정. 둘째만 / 모두 적용 선택 |
| 다과목 할인 | 같은 학생이 같은 월 N과목 이상 | 청구 줄 `cls` 수 | 과목 합산 기준(수강료만 vs 교재 포함) 설정 |
| 재등록 할인 | 직전 학기 · 월 수강 이력이 있고 종료 후 N일 내 재등록 | 수강 이력 | 쿠폰 사용 횟수와 별개로 학생당 1회 등 |
| 신규 할인 | 첫 등록(이력 없음) | 수강 이력 | 재등록과 중복 불가가 일반적(stack 설정) |
| 수급자 · 차상위 감면 | `eligibility_kind` 일치(관리자가 확인 서류 확인 후 표시) | 감면 대상 표시(별도 권한 필드) | **자격 정보는 최소 노출**: 직원은 「감면 대상」 여부만 보이고 자격 종류는 원장만. 서류 보관 방법은 기관 정책 |
| 구성원 할인 | 기관 구성원 구분(재학생 · 교직원 · 졸업생 · 회원) | 회원 구분 | 시설 이용권의 `audience`(student · staff · public, `fac/calc.js` AUDS)와 연결 가능 |

자동 할인은 **청구 생성 · 수납 시점의 서버 계산**으로만 적용하고(클라이언트 값 불신, 01 §5-3의 6번), 적용된 정책 id와 값을 줄에 고정해 이후 정책이 바뀌어도 과거 청구가 변하지 않게 한다.

### 2-5. 중복 규칙(기본값)

1. 기본은 **자동 할인 최대 1건 + 쿠폰 최대 1건**(기존은 쿠폰 1건뿐이라 하위 호환).
2. 정책마다 `stack`을 정한다: `exclusive`(다른 어떤 할인과도 불가) · `stack_with_groups`(같은 그룹끼리만 가능) · `priority`(여러 개가 걸리면 낮은 숫자 먼저).
3. **누적 상한**: 청구 줄의 할인 합계가 정가의 N%(기본 100%, 기관이 낮출 수 있음)를 넘지 않는다. 0원이 되는 청구는 `free`로 기록하되 쿠폰은 사용 처리한다.
4. **계산 순서는 위 §2-2 고정**: 정률은 직전 단계 금액이 아니라 **정가 기준**이 기본(두 정률이 곱해져 의도보다 커지는 일 방지). 순차 적용이 필요한 정책은 `base: 'running'`으로 명시.
5. 바우처 지원금은 쿠폰과 별도 축(지원금은 할인이 아니라 지급 수단)이며, 본인부담 금액에 쿠폰을 쓸 수 있는지는 정책별 `scope.voucher: allow|deny`(기본 deny — 공공 바우처 사업 규정과 충돌 가능, **확인 필요**).

### 2-6. 유효기간 · 횟수

- 기간은 기존 `from` · `until`(KST, `coupon.js` kstDay) 유지. 이용권 · 대여는 **구매 시점 기준**으로 판정(이용 날짜가 아님).
- 횟수는 `limit_total`(기존 `max`) · `limit_per_person` 추가. 횟수는 **원장의 `paid` 수납에 연결된 할인 줄 수**로 센다(이벤트 수 집계 대체).
- 선점(예약 보류): 결제창이 열려 있는 동안 횟수를 잠깐 점유(시설 `fac/sweep.js`의 만료 청소와 같은 TTL). 결제 실패 · 취소 · 만료 시 복원.

### 2-7. 할인과 매출 차감

- **총매출 = 정가 합계, 할인 = 별도 줄, 순매출 = 총매출 − 할인 − 환불**. 현재는 `amount`가 할인 후 금액으로 덮이고 `listAmount`만 보조로 남아(`didisam/coupon.js` LPX.pay 래핑) 정가를 복원하기 어렵다.
- 정책별 할인액이 원장에서 바로 합산되므로 「쿠폰 할인으로 매출이 얼마 줄었나」를 월 보고서 한 줄로 낸다.
- `funded_by: external`(지자체 지원 할인 등)은 **할인이 아니라 지원금**으로 처리(§1-4 바우처로 입력) — 매출이 총액으로 인식되도록.

### 2-8. 환불 시 쿠폰 복원

| 상황 | 기본 처리 | 복원 가능 여부 |
|---|---|---|
| 전액 환불(결제 직후 · 기간 내) | **쿠폰 횟수 복원, 기간이 남았으면 재사용 가능** | 정책 설정 `restore_on_refund`: `always`(기본) · `never` · `ask`(직원 선택) |
| 전액 환불인데 쿠폰 기간 만료 | 횟수는 복원하되 기간이 지났으면 재사용 불가(기록만 복원) | 안내 문구 필수 |
| 부분 환불 | 복원하지 않음(사용된 것으로 간주) | 강제 복원은 원장 승인 + 사유 |
| 자동 할인(형제 · 재등록 등) | 횟수 개념 없음 → 환불 후 재결제 시 조건을 다시 판정 | 해당 없음 |
| 단순 변심 vs 기관 사유 환불 | 기관 사유(폐강 · 휴강)는 `always` 강제 권장 | 대표님 결정(§7) 대상 아님, 기본값으로 시작 |

`led_refund.coupon_restore`(01 §5-1)를 `coupon_restore: none|restored|expired_logged`로 확장하고, 복원 이력은 감사 로그에도 남긴다.

### 2-9. 정책별 보고서

| 보고서 | 열 | 용도 |
|---|---|---|
| 정책별 할인 현황 | 정책 · 기간 · 사용 건수 · 할인 합계 · 평균 할인율 · 환불로 복원된 건수 | 어느 정책이 쓰였나 |
| 매출 영향 | 정가 합계 · 할인 합계 · 순매출 · 할인 비율(품목 유형별) | 할인으로 포기한 매출 |
| 대상별 | 형제 · 다과목 · 재등록 · 신규 · 감면 · 구성원 건수와 금액(감면은 인원 수 · 합계만) | 정책 효과 · 감면 대상 지원 규모 |
| 쿠폰 소진 | 코드별 발행 · 사용 · 잔여 · 만료 | 대량 발행 관리 |
| 이상 징후 | 한 사람이 횟수 상한에 근접 · 같은 코드 짧은 시간 다회 · 할인율 90% 이상 | 부정 사용 점검 |

## 3. 환불 · 부분 환불

### 3-1. 반환 기준 표(근거 → 원장 `rule_type`)

원장의 `led_refund.rule_type`은 상품 유형별로 규정을 선택하고, 규정 계산 결과를 `calc` jsonb에 저장한다(시설 `fac_refund`와 같은 구조). 시설은 기존 `fac/calc.js`(공식 + 테스트 벡터 `tests/fac-vectors.json`)를 그대로 쓴다.

**A. 학원(학원법) 교습비 — `rule_type: hakwon_law`** (S1 해설 기준, **원문 재확인 필요**)

| 반환 사유 발생 시점 | 반환 금액(이미 낸 교습비 기준) |
|---|---|
| 교습 시작 전 | 전액 |
| 교습기간 1개월 이내 — 총 교습시간 1/3 경과 전 | 2/3 |
| 교습기간 1개월 이내 — 총 교습시간 1/2 경과 전 | 1/2 |
| 교습기간 1개월 이내 — 총 교습시간 1/2 경과 후 | 반환 없음 |
| 교습기간 1개월 초과 | 반환사유 발생 **달**은 위 1개월 이내 기준, **나머지(아직 시작하지 않은) 달**의 교습비는 전액 |
| 원격교습(S2) | 납부액에서 **실제 수강한 부분에 해당하는 금액을 뺀 금액**(법제처 2015 해석, 일반 기준보다 우선) |
| 반환 시기 | 사유 발생일부터 **5일 이내**(S1, 원문 확인 필요) |
| 교재비 · 재료비(교습비 외) | 반환 기준표 대상 아님, **실제 제공 · 사용 여부**로 따로 판단(S1) |

- 경과 시간은 **달력 날짜가 아니라 반환 사유 발생일까지 실제 경과한 교습시간**(S1 · S3 비고와 일치) — 결석 · 휴강이 있어도 수업 시간표 기준으로 센다. 구현 시 `led_charge`에 「총 교습시간(분)」 · 「회차 · 시간표」가 필요하다(k12 `S.classes` 시간표에서 계산 가능한지는 **확인 필요**).
- 학원 월 수강료는 월 단위 징수가 일반적이므로 대부분 「1개월 이내」 행을 쓴다.

**B. 평생교육시설 학습비 — `rule_type: lifelong_law`** (S3, 평생교육법 시행령 별표 3, 1개월 이내 · 초과 구조는 위 A와 같음)

| 구분 | 내용 |
|---|---|
| 기관 사유(수업 불가 · 장소 제공 불가, 제28조제4항제1 · 2호) | 이미 낸 학습비를 **일 단위로 계산**해 반환 |
| 학습자 사유(제3호), 1개월 이내 | 시작 전 전액 · 1/3 전 2/3 · 1/2 전 1/2 · 이후 0 |
| 학습자 사유, 1개월 초과 | 시작 전 전액 · 시작 후는 사유 발생 달 + 나머지 달 전액 |
| 원격교육(실시간 제외) | 이미 낸 학습비에서 **실제 학습한 부분 금액**을 뺌. 회차 단위는 열람 · 저장한 회차를 학습한 것으로 봄 |
| 회차 단위 수업 | 잔여 회차 기준 |

디디쌤 강좌(`S.classes`) 중 **어느 것이 학원법 · 평생교육법 · 일반(약관) 대상인지는 기관 유형 설정**(학원 · 평생교육원 · 기타)으로 고르게 한다. 기관 유형별 적용 법령 판단은 **기관(대표님) 확인 필요**.

### 3-2. 수단별 처리 원칙

| 원 수단 | 환불 경로 | 부분 환불 | 원장 처리 |
|---|---|---|---|
| `pg_card`/`pg_easy` | PG 취소 API로 같은 수단 환불(기존 `fac/pay.js:18` `cancel`의 `cancelAmount` 지정) | **가능**(S4). 같은 수납에서 여러 번 부분 취소 가능, 합계 ≤ 원 수납 | `led_refund`에 `pg_cancel_key`. 성공 시에만 `done`. 실패 시 `pending` 유지 + 재시도 |
| `term_card` | 카드 단말에서 취소(전체) 또는 부분 취소. **부분 취소를 지원하는 단말 · VAN인지는 04 문서 확인 후** `partial_cancel_ok`에 기록 | 단말 정책별 | **단말 작업은 시스템 밖에서 일어나므로** 직원이 취소 승인번호를 입력(`cancel_approval_no`)하고 원장은 「단말 취소 확인」 상태로 닫는다 |
| `cash` | 현금 지급 | 임의 금액 | 지급 일시 · 수령자 서명(또는 확인 메모) · 시재(마감)에서 지출로 반영 |
| `bank` | 계좌이체 환불 | 임의 금액 | 환불 계좌 입력(원장 컬럼에 **저장하지 않고** 처리 후 파기, 또는 마스킹 + 별도 암호화 — 개인정보 정책 확인 필요), 이체 완료 체크 |
| `pg_vbank` | 환불 계좌 필요, PG 환불 API | PG별 | 결정 2(가상계좌 도입)와 연동 |
| `voucher` | §3-3 | 사업별 | 지원금 · 본인부담 분리 |
| `pg_overseas` | §3-5 | PG별(PayPal 가능, S5) | 외화 · 환율 규칙 |
| `offset`/`free` | 해당 없음 | — | 쿠폰 복원만 처리 |

**여러 수단이 섞인 수납**(현금 10만 + 온라인 15만, 01 시나리오 ①): 환불 시 **어느 수납부터 돌려줄지**를 선택하게 한다. 기본값은 **마지막 수납부터 역순**(카드 취소가 가능한 쪽을 우선, 기간 임박 순서 검토).

### 3-3. 바우처 환불 — 지원금 / 본인부담 분리 반환

대원칙: **본인부담금은 이용자에게, 지원금은 바우처(원 카드 · 계정)로 되돌린다.** 이용자에게 지원금을 현금으로 돌려주지 않는다. (S6 · S7에 취소 절차 규정이 없어 **구체 방식은 사업별 제공기관 매뉴얼로 확인**하고, 아래는 원장이 반드시 구분해 기록할 구조다.)

1. 반환액 총액 R(규정 계산, §3-1)을 비율로 나눈다: `subsidy_R = R × subsidy_amount / gross_amount`, `copay_R = R − subsidy_R`(끝전은 본인부담 쪽 보정, 10원 미만 내림은 기존 규칙).
2. `copay_R`은 본인부담 수납의 수단(카드 · 현금 등)으로 §3-2 규칙에 따라 환불.
3. `subsidy_R`은 `voucher` 취소(원 사업 시스템에서 승인 취소) → 성공 시 원장 `led_voucher`에 음수 줄, `subsidy_claim_state`를 `claimable` 전이면 금액만 감액, `claimed`/`paid`이면 **환수 대기**(`clawback`) 로 표시해 정산 시 상계.
4. 월말 소멸형 이용권(스포츠강좌이용권 등, S7)의 환불은 **소멸 후 복원 가능 여부가 사업별 규정**이라 화면에 「복원 불가 가능」 경고를 띄우고 확정 전 직원 확인을 받는다(**확인 필요**).
5. 자격 상실 · 대상 변경 시 이후 청구는 일반 단가로 재계산(바우처 사용 중지 안내, S8 일부).
6. 본인부담은 낸 적이 없고 지원금만 쓴 건(본인부담 0원): `copay_R = 0`, 지원금 복원만.

### 3-4. 쿠폰 · 할인분 처리

- 환불 계산은 **실결제액(정가 − 할인) 기준**이다(`01-scenario.md` ③ 유지). 학원법 비율은 낸 금액에 곱한다.
- 쿠폰 복원은 §2-8 규칙.
- 할인 줄은 원 청구에 남고, 환불 줄은 **같은 청구 줄에 음수로** 연결해 「할인 후 금액 − 환불 = 순매출」이 맞게 한다.

### 3-5. 해외 결제 환불 · 환차

(S5에 해외 결제 환율 · 수수료 처리가 없어 **PG 계약서 · PayPal 가이드 확인 필요**. 아래는 원장 규칙 제안이다.)

| 상황 | 제안 처리 |
|---|---|
| 외화 결제, 전체 환불 | 원 수납의 외화 금액 전체를 PG 취소. 환불 원화 = **원 수납의 `amount_krw`**(원 환율 기준, 학습자 불이익 방지 · 매출 차감도 같은 금액). 정산이 이미 끝났다면 PG 환불 시점의 환율 차이는 **환차손익으로 별도 줄**(`fx_diff`)에 기록 |
| 외화 결제, 부분 환불 | 환불 외화 금액 = 원 환율로 환산한 비율. 외화 최소 단위 끝전은 환불 쪽 내림(합계가 원 수납을 넘지 않도록) |
| 해외 수수료 · PG 수수료 | PG가 환불 시 수수료를 돌려주는지 계약별 상이(확인 필요). 원장은 `fx_fee`와 `settle_fee`를 환불 줄에도 기록(0 가능) |
| 3DS 실패 · 승인 거절 | 수납 `failed`(원장 금액 없음) |
| 취소 가능 기한 | 카드 365일(S4). 이후는 PG 환불 불가 → 계좌 송금(해외 송금 수수료 발생)이므로 `manual` 승인 + 사유 필수 |
| 수강생 국가별 세금 · 증빙 | **확인 필요**(국내 현금영수증 대상 아님, 부가세 영세율 여부는 세무사 확인) |

### 3-6. 귀속월 · 원장 승인 · 영수증

- **귀속월**: 기본 = 환불 확정 월에 음수 줄 반영(01 §2-4의 기본값 유지). 월 마감(2차)이 도입되면 마감된 월의 매출은 바꾸지 않고 확정 월에 반영하는 것이 안전하다. **원 청구 월로 소급할지는 세무사 확인 후 대표님 결정**(§7 결정 4).
- **원장(승인) 단계** — 시설 `fac_refund`의 `pending → done / cancelled`에 단계를 얹는다:

| 단계 | 누가 | 조건 |
|---|---|---|
| 신청(`requested`) | 학습자 · 보호자 · 직원 | 사유 입력 |
| 계산(`calculated`) | 서버 자동 | 규정 계산 결과 · 자동 금액 · 근거 줄 |
| 검토(`reviewed`) | 직원 | 금액 수정 시 **사유 필수**, 수정 폭 N% 이상이면 원장 승인으로 격상 |
| 승인(`approved`) | **원장** | 기준 초과(예: 금액 50만 원 이상, 수동 규정, 마감된 날 건, 바우처 환수 발생) |
| 처리(`done`) | 직원 | PG 취소 성공 · 단말 취소 확인 · 현금 지급 · 계좌 송금 완료 중 하나 |
| 반려(`cancelled`) | 직원 · 원장 | 사유 필수, 학습자에게 안내 |

  한 수납당 미결 환불 1건 유일(01 §5-1 `fac_rf_open` 동일), 환불 신청 중에는 그 수납의 추가 환불 신청 차단.
- **환불 영수증**(환불확인서): 환불 번호 · 일자 · 원 결제(수단 · 승인번호 · 카드사 · 결제일) · 원 금액 · 규정 적용 내역(경과 비율 · 근거 법령 표기) · 반환 금액(수단별 · 지원금/본인부담 분리) · 쿠폰 처리 · 예정 입금일(카드는 정산 전 즉시 / 후 약 2~7영업일 안내, S4) · 담당자. 개인정보는 이름 첫 글자만 표시 기본.

## 6. 단계 계획 갱신

### 1차(v41.0)
1. 원장 필드: 수단 열거 · 승인번호 · 카드사 · 할부 · 단말 ID · `partial_cancel_ok` · 정산 상태(§1-1, 1-2).
2. 수납 입력: 현장 카드 단말 **수동 입력**(시나리오 ⑧) + 부분 환불 기록(단말 · PG · 현금 · 계좌).
3. 환불 규정 계산: `facility`(기존) + `hakwon_law`/`lifelong_law`(§3-1, **원문 확인 완료 후 수치 확정**) + 승인 단계(§3-6) + 환불 영수증.
4. 쿠폰: 품목 유형 확장 · 상한 · 1인당 횟수 · 환불 복원 · 정책별 보고서(§2-2~2-9). 자동 할인은 **형제 · 다과목**만 1차.
5. 바우처: **기록 구조 · 지원금/본인부담 분리 · 정산 상태 표시**까지(`led_voucher`, 시나리오 ⑨ · ⑪의 화면). 정산 청구 파일 생성 · 바우처 시스템 연동은 제외.
6. 해외 결제: 필드만 확보하고 **수동 기록 + 원화 환산 표시**(시나리오 ⑫는 PG 계약 확정 후 활성화).

### 2차(v41.x 이후)
1. 단말 · VAN 자동 연동(04 문서 결과 반영) — 승인 · 취소 응답 자동 기록.
2. 바우처 사업별 연동(사회서비스 · 스포츠강좌 · 문화누리 · 평생교육이용권): 가맹 정산 청구 자동화, 환수 상계.
3. 해외 결제 정식 운영(환율 · 수수료 · 환차 자동), 영문 영수증.
4. 자동 할인 나머지(재등록 · 신규 · 감면 · 구성원), 쿠폰 대량 발행 CSV, 이상 징후 알림.
5. 원 청구 월 소급 귀속, 월 마감과 연동.
