# GS 성능 효율성 — 실측 결과와 목표치 (#21)

- 측정 스크립트: `tests/perf/run.js` (서버를 스크립트 안에서 띄우고 끝나면 닫습니다. 백그라운드 서버를 두지 않습니다.)
- 실행: `DATABASE_URL=postgres://…/kit_perf NODE_PATH=… node tests/perf/run.js --n 400 --json out.json` (포트 `PERF_PORT`, 기본 9841)
- 시험 조건: 시험용 가입 코드, `MFA_OFF=1`(2단계 인증 도입 뒤에도 로그인 직후 세션을 받기 위한 **시험 전용** 예외, 운영 기본값 아님), 기관 데이터 학습자 300명 · 과정 20개 · 차시 200개.
- 로그인은 서버 남용 제한(이메일당 10분 8회 · IP당 10분 30회) 때문에 순차 8회만 잽니다. 저장(`PUT /api/state`)은 rev 충돌(409)을 피하려 순차로 잽니다.

해석
- 동시 50에서도 오류 0건, 모든 항목 p95 0.5초 이하입니다.
- 첫 측정 구간(동시 20의 `GET /api/state`)이 동시 50보다 느린 것은 DB 연결 풀 · JIT 예열 영향입니다. 시험기관 측정 전 예열 요청을 보내는 절차를 넣습니다.
- 정적 파일 p95가 동시 50에서 0.4초대로 오르는 것은 1프로세스 · 2 vCPU 한계입니다. 운영(Cloud Run)은 CDN(Cloud CDN · 부하분산기) 뒤에서 정적 파일을 캐시하므로 이 값보다 낮습니다.

## 2. 목표치(시험 신청서 · 제품설명서에 적을 값 — 달성 가능한 현실값)

| 구분 | 조건 | 목표 | 현재 실측 |
|---|---|---|---|
| 화면(HTML · 정적) 응답 | 동시 50 | p95 ≤ 1.0초 | 0.43초 |
| 조회 API(me · state · audit · 학습자 사이트) | 동시 50 | p95 ≤ 1.0초 | 0.23초 |

| 오류율 | 동시 50 · 항목당 400건 | 0% | 0% |

주의
- 운영 배포(`service/gcp/deploy.sh`)는 `--min-instances 0`입니다. 첫 요청은 컨테이너 기동(콜드 스타트) 때문에 수 초가 걸릴 수 있으므로, **GS 시험 기간에는 `--min-instances 1`로 올리고** 시험 환경 · 결과서에 적습니다.
- AI 응답(Claude 호출)은 외부 서비스 시간이 대부분이라 성능 목표에서 제외하고 "외부 연동 응답 시간 별도"로 표기합니다.
- 시험기관 장비(JMeter 등)로 다시 잴 때도 같은 항목 · 동시 수를 씁니다. 이 표는 사전 자체 측정값입니다.
